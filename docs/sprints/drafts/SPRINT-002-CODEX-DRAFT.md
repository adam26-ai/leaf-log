# Overview

Sprint 002 ships geotagged flight photos for the flight detail page. Owners can upload JPEG photos to a flight, Leaf Log stores sanitized downscaled derivatives in Postgres, pins photos on the 2D route when placement is possible, and shows every uploaded photo in a gallery.

The sprint should stay faithful to current Leaf Log patterns:

- Files stay in Postgres for v1, not object storage.
- Heavy image bytes stay off the `Flight` row.
- Routes stay thin and call a shared core in `lib/photos/`.
- Placement and EXIF handling are pure, unit-tested library code.
- Privacy remains app-layer only: every photo list and image serve path must authorize through the same viewer-scoped flight rule as `getFlightForViewer`.

Storage decision: choose Postgres `bytea` with server-side downscaling, EXIF stripping, and hard caps. Do not add object storage in this sprint. Object storage is a reasonable future scaling move, but it adds bucket policy, signed URL, lifecycle, migration, and delete-consistency complexity before the product has evidence that photo volume needs it. For v1, Postgres gives transactional ownership with the flight, simple cascade delete, one backup surface, and matches the house pattern already used for IGC bytes. The key constraint is that Leaf Log must not store originals: store only a display image and thumbnail generated by `sharp`.

# Use Cases

1. Owner uploads photos from a private flight.
   - The owner opens their flight page, selects or drags one or more JPEGs, and sees per-file success or failure.
   - Successful photos appear in the gallery immediately after upload.
   - Photos with usable time or GPS metadata appear as pins on the 2D map.

2. Owner uploads photos from a public flight.
   - Upload remains owner-only.
   - Once uploaded, photos inherit the flight's public visibility for viewers.

3. Anonymous or non-owner views a public flight.
   - They can list photo metadata, load thumbnails/display images, hover pins, and view the gallery.

4. Anonymous or non-owner tries to access a private flight's photos.
   - Photo list routes and image byte routes return `404`, matching flight track/replay behavior.
   - Direct photo URLs do not disclose whether the photo exists.

5. Photo has EXIF GPS.
   - Valid EXIF GPS is used as the placement override because it is usually more precise than timestamp interpolation.
   - The stored image bytes still have EXIF stripped; deliberate coordinates live only in database fields and API JSON.

6. Photo has EXIF `DateTimeOriginal` but no `OffsetTimeOriginal`.
   - Treat `DateTimeOriginal` as local wall-clock time.
   - Convert to UTC using the flight's `localUtcOffsetMinutes`.
   - Interpolate against the replay samples to derive `lat`, `lon`, and optional `altM`.

7. Photo cannot be placed.
   - If there is no usable GPS and no usable timestamp, or the timestamp falls outside the flight window, store the photo as unpinned.
   - Unpinned photos still appear in the gallery.

V1 scope:

- JPEG upload only.
- Multi-photo upload.
- Server-side resize and EXIF stripping.
- 2D map pins and hover preview.
- Gallery thumbnails on the flight page.
- Owner delete.
- Unit, integration, and e2e coverage.

Deferred:

- 3D replay pins.
- HEIC/HEIF input.
- Captions and caption editing.
- Reordering.
- Lightbox/fullscreen viewer.
- Original-file preservation.
- Client-side pre-resize/progress beyond basic batch status.
- Object storage.

# Architecture

Add a `Photo` metadata row and a `PhotoData` byte row. This mirrors the `Flight`/`FlightData` split: lists and page data can select metadata without reading image blobs, while Postgres still owns the file lifecycle.

Proposed Prisma models:

```prisma
model Flight {
  // existing fields
  photos Photo[]
}

model Photo {
  id                         String     @id @default(cuid())
  flightId                   String
  flight                     Flight     @relation(fields: [flightId], references: [id], onDelete: Cascade)

  originalFilename           String?
  contentType                String     @default("image/jpeg")
  displayWidth               Int
  displayHeight              Int
  displayByteLength          Int
  thumbWidth                 Int
  thumbHeight                Int
  thumbByteLength            Int

  takenAt                    DateTime?
  exifLocalDateTimeOriginal  String?
  exifOffsetMinutes          Int?
  flightUtcOffsetMinutes     Int?

  lat                        Float?
  lon                        Float?
  altM                       Int?
  placementSource            String     @default("unpinned") // exif_gps | interpolated_time | unpinned
  placementFailureReason     String?

  createdAt                  DateTime   @default(now())
  updatedAt                  DateTime   @updatedAt
  data                       PhotoData?

  @@index([flightId, createdAt])
  @@index([flightId, takenAt])
}

model PhotoData {
  photoId       String @id
  photo         Photo  @relation(fields: [photoId], references: [id], onDelete: Cascade)
  displayImage  Bytes
  thumbImage    Bytes
}
```

Do not add `caption` in v1. Captions are a deferred product feature and should come with edit UI, validation, and audit expectations instead of an unused nullable column.

Image processing:

- Accept `image/jpeg` or `.jpg`/`.jpeg` only in v1.
- Reject zero-byte files and files over 12 MB before processing.
- Limit batches to 10 files and flights to 40 photos.
- Normalize orientation via `sharp.rotate()`.
- Generate display image: max 2048 px longest edge, JPEG quality 82.
- Generate thumbnail: max 420 px longest edge, JPEG quality 76.
- Do not call `withMetadata()`. This strips EXIF from stored and served bytes.
- Store no original bytes.

EXIF parsing:

- Add `exifr` for metadata parsing.
- Extract `DateTimeOriginal`, optional `OffsetTimeOriginal`, optional GPS lat/lon/alt.
- The source image bytes are discarded after sanitized derivatives and metadata are persisted.

Time bridging:

- EXIF `DateTimeOriginal` is usually local wall-clock time and often lacks `OffsetTimeOriginal`.
- Parse it as naive local components, not as the server timezone.
- If `OffsetTimeOriginal` is present and valid, store `exifOffsetMinutes`, but still prefer the flight offset for v1 consistency unless an implementation test proves common devices need the explicit EXIF offset.
- Convert with the flight's offset:

```ts
utcMs = Date.UTC(year, month - 1, day, hour, minute, second) -
  flight.localUtcOffsetMinutes * 60_000;
```

For example, a flight with `localUtcOffsetMinutes = -420` and EXIF local time `12:00:00` becomes `19:00:00Z`.

If the flight has no `localUtcOffsetMinutes`, leave timestamp-only photos unpinned and record `placementFailureReason = "missing_flight_offset"`. Do not guess from the server timezone.

Placement:

- Reuse the replay sample shape from `lib/igc/replay.ts`: `[lon, lat, altMetres, tOffsetSeconds]`.
- Move the current interpolation logic out of `FlightViz.posAt()` into pure library code or share equivalent logic with `instrumentAt()`.
- For a timestamp-placed photo:
  - `tOffsetSeconds = (takenAtMs - replay.takeoffMs) / 1000`.
  - Require `0 <= tOffsetSeconds <= replay.durationS`.
  - Do not clamp out-of-window photos to endpoints in v1; leave them unpinned to avoid false placement.
  - Interpolate lon/lat/alt from bracketing replay samples.
- For EXIF GPS:
  - Use GPS as placement source when lat/lon are finite and within an inflated flight bounds sanity check.
  - Store `takenAt` too when available, but placement comes from GPS.
  - If GPS fails sanity validation, fall back to timestamp interpolation.

Core flow:

- `POST /api/flights/[id]/photos` authenticates the session, verifies the viewer is the owner of the flight, parses form files, and calls `addPhotos({ flightId, ownerId, files })`.
- `addPhotos()` loads the flight and `FlightData.rawIgc`, builds replay samples once per batch, processes each image, computes placement, and writes `Photo`/`PhotoData` rows in a transaction per accepted file.
- A failed file should not fail the whole batch unless the request itself is invalid.

Read flow:

- `GET /api/flights/[id]/photos` returns metadata only, authorized by `getFlightForViewer(id, viewerId)`.
- `GET /api/flights/[id]/photos/[photoId]` serves sanitized image bytes, authorized by `getFlightForViewer(id, viewerId)` and `photo.flightId === id`.
- Use a `variant=thumb|display` query parameter, or separate `thumb` route if that is cleaner in Next 16.
- Return `404` for unauthorized, missing flight, missing photo, or mismatched flight/photo.
- Use `cache-control: private, max-age=300` for private-compatible browser caching. Public CDN caching can be revisited later.

UI:

- `FlightViz` fetches photo metadata alongside track/replay.
- `TrackMap` receives pinned photo metadata and renders a `photos` GeoJSON source/layer after every style load, the same way it re-adds track and cursor layers.
- Hovering a photo pin shows a small preview that loads the authorized thumbnail route.
- A gallery component renders thumbnails below the map/replay block. Pinned and unpinned photos both appear. Unpinned photos get a subtle "Unpinned" status for owners only.
- Owners get upload and delete controls; non-owners never see them.

# Definition of Done

- Owners can upload one or more JPEG photos to their own flight.
- Uploaded photos are stored only as sanitized downscaled JPEG derivatives in Postgres.
- No original photo bytes are retained.
- Photo metadata list queries do not select image bytes.
- Photos with valid EXIF GPS are pinned from GPS.
- Photos with usable EXIF `DateTimeOriginal` are converted to UTC using `flight.localUtcOffsetMinutes` and pinned by replay interpolation.
- Photos without usable placement metadata remain unpinned but visible in the gallery.
- The 2D map renders photo pins and hover previews.
- The flight page renders a thumbnail gallery for owners and authorized viewers.
- Upload and delete are owner-only.
- Public flight photos are visible to anonymous/public viewers.
- Private flight photos return `404` to anonymous users and non-owners from both list and serve routes.
- Served image bytes contain no EXIF metadata.
- 3D pins, HEIC, captions, reordering, lightbox, originals, and object storage are explicitly deferred.
- `pnpm build`, `pnpm test`, `pnpm typecheck`, `pnpm lint`, and `pnpm e2e` pass.

# Risks

- EXIF timezone ambiguity is the main correctness risk. Mitigation: treat `DateTimeOriginal` as local wall time, use the flight's derived offset, unit-test the conversion, and avoid server timezone parsing.
- Camera clocks can be wrong. V1 should not add manual correction; unpinned gallery photos are acceptable. A later sprint can add owner-adjustable time offset if this is common.
- Postgres growth can become real if users upload many photos. Mitigation: no originals, downscale aggressively, enforce caps, and keep object storage as the scaling path once usage proves the need.
- MapLibre style changes wipe custom layers. Mitigation: add photo layers through the same re-add path currently used for track and cursor.
- EXIF GPS can be stale or wrong. Mitigation: sanity-check coordinates against inflated flight bounds and fall back to timestamp placement.
- E2E pin verification may be structural rather than pixel-perfect due to headless map rendering limits.

# Security

- Photos inherit flight visibility. There is no separate photo visibility in v1.
- All photo reads must authorize the parent flight through `getFlightForViewer(id, viewerId)` or an equivalent helper that applies the same predicate.
- Serve routes must return `404` for unauthorized access.
- Upload and delete must be owner-scoped. A public viewer cannot add or delete photos on someone else's public flight.
- The image route must verify both route params: the photo exists and `photo.flightId === params.id`.
- Never expose raw original uploads.
- Strip EXIF by writing sanitized derivatives with `sharp` and not preserving metadata.
- Keep coordinates in JSON/database fields only, not embedded image metadata.
- Validate file size, count, MIME/type, and decoded image dimensions.
- Use `content-type: image/jpeg` and `x-content-type-options: nosniff` on image responses.
- Do not add public bucket URLs or unauthenticated static file paths.

# Open Questions

1. Should `OffsetTimeOriginal`, when present, override `flight.localUtcOffsetMinutes`, or should v1 always use the flight offset for consistency? My recommendation is flight offset first, store EXIF offset for diagnostics, and revisit only if real uploads show mismatches.
2. Are the proposed caps acceptable for v1: 12 MB input, 10 files per batch, 40 photos per flight, 2048 px display, 420 px thumbnail?
3. Should GPS sanity validation use inflated flight bounds only, or nearest-route distance? Bounds are cheaper and probably sufficient for v1; nearest-route distance is stricter but more code.
4. Should unpinned owner-visible status show the reason, or just say "Unpinned"? My recommendation is a terse owner-only reason for debugging camera metadata issues.
5. Should photo deletion be hard delete only? My recommendation is hard delete, because photos are user-owned media and cascade naturally with flights.
