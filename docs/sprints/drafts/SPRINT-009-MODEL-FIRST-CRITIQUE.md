## Strengths

- Decision 4 (mutable `flight.instructorId` vs. immutable `instructorId`/`signedByProfileId` on `InstructorNote`/`RatingSignoff`) is a real, well-reasoned design point — it correctly anticipates that reassignment/unfriending must never reattribute or delete history, and use cases 4–5 demonstrate it concretely.
- Decision 5's split of read-privacy between `RatingSignoff` (readable by current instructor too) and `InstructorNote` (author-only, frozen) is a subtlety a rushed bolt-on could easily get wrong.
- The "PR1 = zero UI, proven only by DB-backed integration tests, including negative cases" plan correctly follows the `statsFrom` test-convention precedent and is genuinely thorough (Authorization matrix + Test strategy sections cover every actor × action cell).
- Correctly identifies that `RatingSignoff.flightId` being non-nullable is a deliberate scope fence against the ground-school-hours question (Open Question 3), rather than silently begging it.

## Gaps and Risks

- **PR1 (45% of the sprint's effort) ships nothing a pilot can see, and nothing the auto-calc criteria need.** The stats/criteria work that requires zero schema and zero authz — flight count, flying days, total airtime, site diversity, glider diversity (once `glider` is added to the list-item selection) — is not scheduled until **PR4**, the last PR, gated behind the entire instructor/signoff authorization model in PR1–PR3. Per the codebase facts, `statsFrom`'s dedupe idiom is a pure, already-proven pattern with no dependency on `instructorId`/`InstructorNote`/`RatingSignoff` existing at all. Coupling ~70% of the visible page (the auto-calculable majority, per the USHPA brief) to 85% of the sprint's authz effort is an unexamined sequencing choice — the draft's own Risks section never asks "could the auto-calc slice ship independently of PR1's authz work?"
- **PR2 ships a dead-end control.** "Instructor" and "Flight type" pickers land on the edit page in PR2, but there is no `/ratings` page (PR4) and no instructor-facing view (PR3) yet for a pilot to see any effect of assigning an instructor. A pilot who picks "Alex" in PR2 gets no page, no note, no signoff, no explanation anywhere in the product for two more PR cycles — worse than ship-first's own PR3 (which at least ships *after* PR1's live page already exists to contextualize why instructor assignment matters).
- **All of PR1's investment is a total write-off if the sprint is interrupted or reprioritized after PR1.** Given `AGENTS.md`/`CLAUDE.md`'s PR-per-branch, ask-before-merge workflow, and this project's own established pattern of iterative, live-verified rounds (per this session's project memory — UI work here is driven in short rounds, not one big upfront spec), a plan whose first mergeable milestone produces zero demoable output is a mismatch with how this repo actually ships. Ship-first's PR1 (35% effort) is a complete, demoable increment even in isolation; model-first's PR1 is not.
- **DoD's "verified by manual QA pass finding nothing different, not just by the absence of new routes" is a strange first use of this team's manual-QA discipline.** The project memory explicitly calls out manual QA as a *live exploratory* pass before merge — spending that practice's first application in this sprint on confirming *nothing changed* (PR1) rather than exercising an actual new page is a weak return on the gate, and defers the pass that would surface real UX problems (locked-row treatment, whether asymmetric instructor-nomination feels invasive) to PR3/PR4, by which point the schema and authz shape are already frozen and "provably right" under tests nobody outside the team has used.
- **Open Question 1 (should instructor nomination require the instructor's consent?) is explicitly punted to "revisit... once PR3 ships to real users" — but PR3 (the instructor-facing view) is 85% of the way through the sprint.** That's a long time to carry a possibly-wrong asymmetric-consent design in production schema/authz before any real signal comes back, compared to a sequencing where the low-stakes page ships first and gathers reaction while the consent question is still open.
- **The "avoid a painful migration" argument for schema-first (Risks: "Schema churn if the per-flight instructor-assignment shape proves wrong") doesn't actually hold up against the draft's own Open Questions.** Open Questions 2 and 3 (cross-flight instructor read access, pilot-level non-flight criteria like ground-school hours) are real unresolved shape questions baked into the "committed" v1 schema (e.g. `RatingSignoff.flightId` required). If either resolves toward "we got this wrong," model-first needs a follow-up migration anyway — the complete-model-first bet doesn't eliminate the rework risk it's justified by, it just moves the unresolved parts into open questions decided with zero production usage data instead of with some.

## Questions for the merge

1. Should the auto-calc slice (glider added to `LIST_SELECT`, `criteria.ts`'s auto rows, a stats reducer, and a first version of `/ratings`) be pulled out of model-first's PR1/PR4 and shipped as an early, schema-free milestone regardless of which draft's authz design is adopted — since the codebase facts show it has no real dependency on the instructor/signoff work?
2. If model-first's authz-first sequencing is kept, should PR2 (instructor/flight-type pickers) be resequenced to land *after* some visible ratings surface exists, so pilots aren't handed a control with no observable effect for two PR cycles?
3. Given Open Question 1 (instructor-consent) is explicitly meant to be revisited from real user reaction, does it make sense to lock the asymmetric-nomination schema/authz in PR1 before any user has seen an instructor-facing surface — or should that decision be deferred until after some live signal, even if it costs an additive migration later?
4. Is 45% of the sprint's effort an acceptable amount of unshippable-in-isolation work to place at the front of the plan, given this repo's PR-per-branch/ask-before-merge workflow and its track record of short, live-verified iterative rounds — or should the "complete domain model" be broken into a smaller authz-core PR plus a separately-mergeable extension, so a mid-sprint stop still leaves something users can see?
5. Do `RatingSignoff`'s revocation fields (`revokedAt`/`revokedByProfileId`) need to exist in v1's schema at all, or is append-only (as the other draft proposes) sufficient until a real correction need is observed — since adding revocation later is additive, while carrying unused revocation semantics through the full authz-matrix/test-strategy buildout now is pure sunk cost if it turns out unneeded?
