# Wing editor

Settings includes a Wings card directly beneath Profile. It lists the signed-in pilot's exact stored wing names and flight counts, including unspecified wings. Select one name to rename it or multiple names to merge them, then enter the final name (existing names are suggested).

One selected wing uses blue Rename prefixes, a Rename wing to label, and a Rename Wing button. Multiple selections switch to deep emergency-orange Merge prefixes, checkmarks, label and Merge Wings button. The warning uses deep orange on a light orange background, previews how many entries will change, and identifies a merge into an existing name. Saving is explicit; typing, selecting, pressing Enter in the name field and Cancel do not save. Wing controls are isolated from the surrounding profile form's autosave behavior.

Saving updates `Flight.glider` for the authenticated owner and selected exact source names, and applies the resulting wing's tandem default to inherited flight flags in one transaction. It preserves manual tandem/solo overrides, other flight flags, notes, flight data, scores and privacy. Source counts are rechecked before updating; stale selections or concurrent transaction conflicts prompt a refreshed review rather than a partial update. Destination names are trimmed, required, single-line and limited to 200 characters, matching the individual flight editor.

No separate wing registry or upload alias is created. Subsequent uploads continue to use the name recorded in their IGC file and may introduce an old spelling again. Existing original IGC bytes are preserved. Renaming does not trigger metric or XC recalculation.

The upper-right **Enable tandem** switch is available to every pilot and defaults to off. It reveals a two-person switch after each named wing's selection checkbox and visibility button. Unspecified wings must be named before they can have a tandem default. Disabling Enable tandem hides the controls; it retains saved wing defaults and continues applying them to future flights.

`Profile.tandemWings` stores exact wing names. Toggling a wing updates both existing inherited flights and future web/device uploads, manual entries and CSV imports. `Flight.tandemOverride` is nullable: null follows the wing, true is an explicit tandem choice, false an explicit solo choice. `flightFlags` and legacy `occupancy` stay synchronized for badges, filters and ratings. Only changing tandem/occupancy establishes an override; saving notes or another flight type does not. Explicit CSV occupancy and upload choices also take precedence. Reassigning a flight to a different wing reapplies defaults only when its override is null. Duplicate uploads never replace a prior choice. Profile row locking serializes wing changes with uploads and flight edits so concurrent operations cannot leave a new flight with a stale default.

When tandem controls are enabled, merges require a visible **Merged wing is tandem** choice. The initial proposal is OR across the selected wings and any existing destination wing. The pilot can override that proposal before saving. The resulting default applies to inherited flights from all merged wings, including an existing destination, and preserves each manual override. A rename retains the source default. With controls hidden, merges retain the OR default automatically. Renames/merges move the saved default to the resulting name; future uploads must record that exact name.

The tandem migration preserves historical explicit occupancy (including solo) and tandem flags as overrides; previously unchosen flights inherit wing defaults. No rating verification is required to enable the controls.

Validation covers authentication/input rejection, owner isolation, merging into an existing name, unspecified wings, stale-count rollback, preservation of other flight fields, explicit Save versus profile autosave, and Cancel. Tandem checks cover the migration, repeated toggling, manual overrides, device and web uploads, deduplication, CSV/manual entries, wing reassignment, hidden controls, merge proposals and concurrent uploads. Browser checks use temporary flights to verify mobile/desktop layouts, merge and rename persistence, and refreshed logbook filters.
